# Intent: wiki-style documentation site on GitHub Pages

## Problem

Everything a user or contributor needs to know lives in two Markdown files:
`README.md` (603 lines) and `CONTRIBUTING.md` (150 lines).

- **One long page for everyone.** The README mixes user onboarding
  ("Getting started", installation, the per-agent table) with maintainer
  material: per-skill maintenance sections, automatic updates and the token.
  A newcomer has to scroll past maintainer detail. A maintainer cannot link
  to one focused page.
- **No place for explanation.** How sources are pinned and refreshed, why
  some references are generated and others written by hand, what the
  security model is, and how the Nix style check works are all questions
  users ask. Today the answers are scattered across the README, AGENTS.md,
  CONTRIBUTING and the intent, spec and plan files, if they are written down
  at all.
- **Facts drift.** The skill list, the pinned upstream revisions, the licence
  of each skill and which skills update automatically are repeated by hand
  in several README sections. The truth is in `skills.json`, each
  `sources.json` and the updater's skill list in `update.yml`. #37 and #41
  each had to fix several hand-kept lists (`ln -s` lines, the Home Manager
  example, the invocation line).
- **No website.** GitHub Pages is not enabled (`has_pages: false`). The
  repository is public, so a site costs nothing, and it is where people
  expect documentation for a Nix project to live. The upstream projects the
  skills point to, such as agent-box and microvm.nix, publish mdBook sites.
- **The next tasks need somewhere to land.** The demo VM (#57) and the
  templates (#58, #59) need tutorial and how-to pages.

## Proposed outcome

- **A public site** at `https://olafkfreund.github.io/nix-skills/`,
  organised like a wiki into:
  - **tutorials** (learn by doing): getting started, and later the demo VM;
  - **how-to guides** (one task each): install per agent, update and roll
    back the pin, contribute a skill, fix discovery, narrow the update
    token;
  - **reference** (look-up): the skill catalog, the Home Manager module
    options, the Nix style rules, the update schedule;
  - **explanation** (why): why skills, hand-written versus generated
    references, how sources are pinned and updated, the security model.
- **Generated facts.** The skill catalog and the update schedule are built
  from the repository's own data, so they are always correct for the commit
  that built the site.
- **Reproducible.** The site builds with Nix, offline, in CI. Pull requests
  check that it builds and that its links resolve. Merges to `main` publish
  it.
- **A shorter README.** It becomes a landing page: what the project is, the
  shortest install, the start prompt, and links into the site. Nothing is
  lost; detail moves to the site.

## Affected users and systems

- Users and contributors of the collection, who get a documentation site.
- New files: `docs/` (site sources), a docs build output in the flake, a
  generator for the catalog pages, and a Pages deployment workflow.
- Changed files: `README.md` (shortened, with links to the site), and
  possibly `CONTRIBUTING.md` and `AGENTS.md` for the new layout and checks.
- A repository setting: **Settings → Pages → Source → GitHub Actions**,
  enabled once by the owner.
- No change to skills, providers, updaters, the Home Manager module or the
  skill packages. No host is changed.

## Constraints

- **Offline and reproducible.** The site builds from the repository alone,
  with pinned tools from the existing flake input, without network access,
  so CI and local builds match.
- **Generated, not copied.** Catalog and update facts come from
  `skills.json`, `sources.json` and the workflow's skill list at build time.
  They are never hand-maintained. Upstream reference text is linked from the
  site, not republished there. Its licences stay attached to the skill
  packages.
- **Least privilege for publication.**
  - PR jobs stay read-only with no secrets.
  - Only the deploy job on `main` gets `pages: write` and `id-token: write`.
  - No personal token is used.
  - Branch protection on `main` is unaffected.
- **Scope of the flake.** AGENTS.md describes `flake.nix` and `nix/` as
  "data packages and opt-in Home Manager installation". A docs output widens
  that description slightly; AGENTS.md is updated to say so.
- **Nothing lost from the README.** Every current README fact either stays
  or moves to a site page, and anchors that other files link to keep
  working, or their links are updated. CONTRIBUTING links to
  `README.md#automatic-updates`.
- **The Nix style rules apply to the site's authored pages too**: no
  unnecessary quoted names, no `/nix/store` searches.
- **Tool choice is future-proof.** mdBook is maintained and in nixpkgs
  (0.5.4 at the pinned revision). MkDocs Material is in maintenance mode
  since early 2026 and was ruled out.
