# Intent: a readable skill catalog

## Problem

The [skill catalog] page, generated by `scripts/docs_catalog.py` on every
site build, is the site's main reference for which skills exist and where
their content comes from. It does not display properly.

The table was measured in the browser on 2026-09-24, against mdBook's
750 px content column:

- **It overflows.** The table has six columns (Skill, Description, Kind,
  Upstream, Pinned, Licence) and is 1007 px wide in the 750 px column. It
  scrolls sideways, so Pinned and Licence are off-screen unless the reader
  finds the scrollbar.
- **Descriptions are unreadable.** All ten descriptions, up to 256
  characters each, are squeezed into a column about 130 px wide, one or two
  words per line, as the owner's screenshot shows.
- **The cell text is poor:**
  - upstreams are raw, unlinked URLs (`https://github.com/cachix/devenv`,
    `https://wiki.nixos.org/wikidump.xml.zst`);
  - "generated from upstream" repeats on eight of ten rows;
  - pins are bare hashes (`master 0b2f1129177f`) with no link to the
    upstream revision.
- **One more table overflows.** The per-agent table on "Install the skills"
  is 751 px against 750 px. A 1 px overflow adds a horizontal scrollbar.

The other six tables on the site fit within the column. The update schedule
and module options pages use lists, not tables, and display correctly.

[skill catalog]: https://olafkfreund.github.io/nix-skills/reference/catalog.html

## Proposed outcome

- **The catalog fits and reads well.** No horizontal scrolling at mdBook's
  default width. Every skill's description is readable as normal prose.
- **Useful, linked facts:**
  - the upstream is shown by name and linked;
  - the pin links to the exact upstream revision where one exists;
  - the licence is named and linked to the skill's licence file;
  - hand-written skills are clearly marked as such.
- **Still generated** from `skills.json`, each `SKILL.md` and each
  `sources.json`. Nothing becomes hand-maintained.
- **The install table fits,** with no scrollbar and no information lost.
- **Checked.** A regression test or build check makes a returning
  overflow, or cramped cells, unlikely to go unnoticed.

## Affected users and systems

- Readers of the documentation site, especially anyone checking which
  skills exist and where their content comes from.
- Files: `scripts/docs_catalog.py` and its tests in `tests/test_docs.py`;
  `docs/src/how-to/install.md`; possibly site styling (`docs/book.toml`, a
  small CSS file) if the spec chooses a styling fix.
- No change to skills, `sources.json`, providers, updaters, modules or CI
  behaviour.

## Constraints

- **Generated from repository data.** The fix must not introduce
  hand-kept facts. Licence names, if shown, come from the licence files or a
  reviewed mapping the tests cover.
- **No wider page.** Enlarging mdBook's content width for the whole site
  would hurt readability everywhere; the fix belongs to the tables.
- **Links are real.** Revision links point to the recorded upstream
  revision. Sources without one, such as the wiki dump's snapshot hash, are
  not given invented URLs.
- **Existing checks still apply:** `check_docs.py` (links, anchors, Nix
  style, `SUMMARY.md`), the generator's fail-loud checks, and the
  intent → spec → plan gates.

## Open questions

- **Catalog layout.** A compact overview table (for example Skill, Source,
  Licence) followed by one short section per skill with its description and
  pin, or keep a single table with fewer columns and the description
  underneath each name?
- **Licence names.** Show them (Apache-2.0, MIT, LGPL-2.1), which needs
  either detecting them from the licence file text or a small reviewed
  mapping, or only link the licence file?
- **Guarding against a repeat.** A generator test on table width (column
  count and cell length limits), or a browser-based check? The latter is
  heavier, and not available in offline builds.
