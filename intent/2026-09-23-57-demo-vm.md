# Intent: a disposable NixOS demo VM for agentic coding

## Problem

A new user who wants to try AI coding agents with these skills on NixOS
currently has to change their own system first:

- add flake inputs;
- enable the Home Manager module;
- pick and install an agent;
- optionally set up Podman;
- rebuild.

The documentation site's [Getting started] tutorial describes this, but:

- **There is no way to try before committing.** Every step changes the
  user's real configuration. Someone evaluating the project, or unsure which
  agent to pick, has nothing safe to run.
- **The onboarding path is untested end to end.** Each piece is tested
  separately: the module builds a test home, the skills validate, the site
  builds. Nothing proves that an agent on a real NixOS system actually has
  the skills in its skill directory and can be started. The README and site
  still say discovery is untested for OpenCode and Antigravity.
- **Running agents directly on your machine exposes it.** An agent there can
  read everything you can, including `~/.ssh`, cloud credentials and
  `.env` files. A first experiment is exactly when a user should not give an
  unfamiliar agent that access.
- **Nothing shows the whole stack together.** The `nixos-coding-agents`
  skill describes agents from llm-agents.nix, Podman and agent-images, and
  devenv, but a user never sees them working together on one system.

[Getting started]: https://olafkfreund.github.io/nix-skills/tutorials/getting-started.html

## Proposed outcome

- **One command, nothing changed.** A user with Nix and a Linux machine that
  supports KVM starts a NixOS demo VM with one command, and nothing on their
  own system changes.
- **Everything ready inside:**
  - one or more coding agents of their choice, from llm-agents.nix;
  - these skills installed for each of those agents;
  - Podman for the sandbox examples, and devenv;
  - a small sample project to try the start prompt on.
- **Their credentials, not ours.** The user signs in or supplies their own
  API key inside the VM. No secret is ever built into the image.
- **Disposable.** Deleting one disk file resets it.
- **It is the tested reference system.** A NixOS VM test in CI boots it and
  proves that the agents are installed and that each agent's skill
  directory contains the skills. That makes it the end-to-end check of the
  onboarding path that is missing today.
- **Documented.** A tutorial page on the site ("Try it in a demo VM") walks
  through starting it, adding a key, and giving the start prompt.
- **Reusable.** Its configuration can later be reused by the starter
  template (#58).

## Affected users and systems

- New users evaluating the collection or choosing an agent.
- Maintainers: CI gains a job or check that boots a VM.
- New files: the demo configuration and its runner, the VM test, and a
  tutorial page in `docs/src/`. Possibly a separate flake for the demo, so
  its inputs do not affect users who only install skills.
- Changed files: `docs/src/SUMMARY.md`, AGENTS.md (layout), CONTRIBUTING if
  the checks change, and CI workflow files.
- No change to the skills, the Home Manager module's behaviour, providers or
  updaters. Nothing runs on the maintainer's or user's host beyond the VM.

## Constraints

- **No impact on skill users.** People who only add `nix-skills` as an
  input must not have to lock or download llm-agents.nix, agent images or VM
  tooling.
- **No secrets in images or CI.** API keys and logins happen inside a
  running VM. The CI test starts agents only for `--version` or `--help`
  and never calls a model.
- **Pinned and reproducible.** The demo's inputs are locked. It follows
  llm-agents.nix's rule of nixpkgs-unstable only, without `follows` onto a
  stable release.
- **Licences are visible.** Some agents are unfree binaries. The demo names
  which agents it includes, and they carry upstream's licence labels.
  Choosing agents stays with the user.
- **CI stays usable.** A VM test needs KVM. GitHub's standard Linux runners
  have had `/dev/kvm` since January 2024, but it needs a udev rule and is
  sometimes unavailable. The design must decide whether the VM test is part
  of the required status or a separate, non-blocking job, so a missing KVM
  device never blocks unrelated pull requests.
- **Resource use is stated.** Disk image size, RAM and download size are
  documented, because agent binaries and a desktop-free NixOS still take
  several gigabytes.
- **Existing rules still apply:** the Nix style rules, the documentation
  checks, and the repository's intent → spec → plan gates.

## Open questions

- **Which agents by default?** Proposed: Claude Code, Codex and OpenCode,
  with Gemini CLI optional. Or ask the user to choose at build time?
- **Where it lives.** A `demo/` subflake (`?dir=demo`), or outputs of the
  main flake?
- **Which VM technology?** NixOS's built-in QEMU VM (`build-vm`
  style), or microvm.nix, which the collection already has a skill for?
- **CI placement.** Should the VM test be required for merging, or run as a
  separate, non-blocking workflow on pull requests that touch the demo, plus
  on a schedule?
- **Graphical or console?** Console-only (SSH or serial login) keeps it
  small. A desktop would suit agents with a GUI, such as the Claude
  desktop app, but costs much more.
