# Intent: Nix idioms and best practices from nix.dev

## Problem

User feedback said the `nix-language` skill "needs more description of idioms
and best practices". The skill quotes the Nix reference manual (syntax,
evaluation, built-ins). The manual describes what the language does, not how
experienced users write it. Agents therefore produce code that works but that
reviewers reject, for example:

- `rec { … }` sets that recurse by accident;
- wide `with pkgs;` scopes that hide where names come from;
- `<nixpkgs>` lookup paths that depend on the caller's environment;
- impure `fetchTarball` calls without hashes;
- reproducibility mistakes around `builtins.path` and file sets.

The authoritative source for this guidance is the NixOS project's own
nix.dev. Its `source/guides/best-practices.md` covers:

- URLs;
- `rec` sets;
- `with` scopes;
- `<...>` lookup paths;
- updating nested attribute sets;
- reproducible Nixpkgs configuration;
- reproducible source paths.

`nix-workflow` (#24) covers command-line habits, not how to write
expressions, so this gap remains.

## Proposed outcome

An agent writing or reviewing Nix expressions has pinned, attributed nix.dev
best-practice guidance available. It applies these idioms, explains them when
reviewing, and cites them. The guidance regenerates from nix.dev with the
collection's usual provenance, hashing and weekly update process.

## Affected users and systems

- Users and agents writing or reviewing Nix code, through the collection.
- A skill package: a new one, or `nix-language` (open question).
- Provider code:
  - `github_docs` copies whole files, but reads only a file named `LICENSE`,
    and nix.dev has `LICENSE.md`;
  - it also does not understand nix.dev's MyST markup.
- Registration (check, update, artifact, workflows, `devenv.nix`,
  `skills.json`, README) and weekly updater enrollment, if a new maintained
  skill is added.

## Constraints

- **Licence:** nix.dev is CC-BY-SA-4.0.
  - Adapted excerpts must carry attribution, a licence link, and a notice
    that they were modified, and must stay under CC-BY-SA-4.0.
  - `nix-language` currently ships Nix manual text under LGPL-2.1 (its
    `COPYING`). The two licences must stay clearly separated per file, and
    the repository must not relicense either.
- **Markup:** nix.dev is written in MyST. Uses in `best-practices.md` include
  ```` ```{code-block} nix ````, `:::{tip}` and `:::{note}` admonitions,
  `(label)=` targets, a `{contributors}` directive, and roles such as
  `{ref}`. Output must be portable Markdown for agents. Unknown MyST
  constructs must fail closed, not pass through silently.
- **Pinned and reproducible,** like the other providers: a recorded revision,
  input and output hashes, and `update.py --check`.
- **Selection** is reviewed policy that automation cannot change.
- **Keep packages loadable:** the page is 7.5 KB. Any other pages added must
  justify their size.

## Open questions

- **Where it lives:** a new small `nix-best-practices` skill, or a reference
  inside `nix-language`?
  - A new skill keeps one upstream and one licence per package, which is how
    every maintained skill here works. `nix-language`'s SKILL.md can then
    point to it.
  - Inside `nix-language` would mean a second upstream, a second licence file
    and a second generator in one package.
  - Recommendation: a new skill.
- **Scope:** `best-practices.md` only, or also selected nix.dev guides such as
  `recipes/dependency-management.md` (pinning with npins) and `faq.md`?
  Recommendation: `best-practices.md` only for now, with further pages as
  reviewed selection changes later.
- **MyST handling:** convert the constructs used (code blocks to fenced code,
  admonitions to labelled blocks, targets to anchors, `{ref}` to links,
  `{contributors}` dropped) and reject anything else; or copy the raw MyST?
  Recommendation: convert and fail closed. Raw MyST confuses agents and
  breaks Markdown rendering.
