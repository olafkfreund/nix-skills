# Plan: Source-maintained Nixpkgs skill

## Approved decisions

Create portable `skills/nixpkgs-development/`, independent of sibling skill
installations and machine-specific policy. Include a short, normally discoverable
`SKILL.md`, four references (`packaging.md`, `customization.md`, `helpers.md`,
`library.md`), `sources.json`, and upstream `COPYING`. Preserve applicable MIT
attribution and notices separately from the sibling licenses. Additional required
notices require reviewed package/allowlist changes.

Track weekly snapshots of `NixOS/nixpkgs` **master**, initially
`7561e7e3e12a06677b1525a12bcccb0b4e4c601d`. Its `.version` value `26.11` is
development-series metadata, not a stable-release or channel-promotion claim.
Never substitute a channel, ambient registry, or `<nixpkgs>` for this pin.
Resolve master once per update and fetch/verify that full SHA. Automatic updates
require descendant ancestry; rewinds, divergence, missing sources, and failed
ancestry verification stop publication. Explicit repinning is reviewed work.
An identical SHA is a no-op; an advanced SHA is regenerated and tested even if
the selected prose did not change. Identify provenance-only changes in reports.

Expose `--skill nixpkgs-development` with `--latest`, `--revision <full-sha>`, and
`--check`; reject flags inappropriate to each skill. Preserve existing Nix and
devenv interfaces and generated bytes. Use explicit trusted skill identities,
upstreams, branches, and allowlists, with focused Nixpkgs logic in
`scripts/nixpkgs.py` and standard-library Python. Reuse proven helpers where
semantics match; introduce no general plugin framework or duplicate updater.

Generate the selected library reference through the pinned source's
`nixpkgs-manual.lib-docs` derivation, which uses its `nixdoc`,
`doc/function-catalog.json`, and `lib/` to produce `lib-functions.json`.
Validate the actual schema and API identities. Do not parse Nix comments with a
new regex extractor, use host nixdoc, or rebuild the entire manual.
Use independently recorded Nix 2.35.2 at
`2c73b59da29606068c0c98db015dd3a66955525d` through the existing pinned-tool helper;
automatic Nixpkgs updates cannot change this tool pin or follow the sibling
manifest. The host Nix only bootstraps it. Build generators separately, without
new import-from-derivation expressions. Imports use the exact checkout and
explicit system/config/overlays.

The manifest records upstream/branch/revision/version, curated paths and
anchors/headings, API identities/aliases, consumed inputs, generated JSON and
output hashes, coverage hashes, and the evaluator pin. Use deterministic
serialization without timestamps, temporary paths, or credentials. Hash the
catalogue, generators, relevant library sources, nixdoc package definition, and
consumed includes/mappings. Branch, selection, and toolchain policy are immutable
to automated PRs. Hash documentation/library coverage, not unrelated package or
binary payloads. Generated prose describes source comments; semantic evaluation
is a separate claim. Verify declaration paths and cite exact source revisions.

Keep the entrypoint focused on writing, explaining, reviewing, and debugging
Nixpkgs packages/APIs. Inspect the consumer's repository, lockfile and actual
Nixpkgs pin; distinguish evaluator versions and build/host/target platforms.
Preserve package-set conventions, overlays and chosen environment tooling.
Explain `override`, `overrideAttrs`, overlays and module merging, dependency
roles, setup hooks, `runHook`, hashes, checks and metadata. Temporary fake hashes
are discovery aids, not finished recipes. Do not disable checks, sandboxing or
hardening to hide an unexplained failure. Respect existing authorization and
distinguish evaluation, builds and runtime tests. Generic module coverage is not
an exhaustive NixOS/Home Manager option catalogue or authorization to deploy.

## Steps

1. **Inspect the baseline and integration dependency.** Read applicable repo
   instructions and the existing packages, updater, validator, artifact handling,
   tests, workflows and README. Record the integration base and sibling hashes.
   Run available sibling checks before editing shared code. Check devenv PR #4:
   once merged through its normal authorized process, bring the task branch up
   to date with that reviewed base. Do not merge #4 without authorization or
   copy its commits implicitly. If still open, complete independent source,
   converter and fixture work before reporting the shared-tooling dependency.
   Verify: clean/understood worktree, recorded baseline, passing existing checks,
   and an explicit account of which integration prerequisites are available.

2. **Verify pinned inputs and record exact selections.** Fetch the agreed Nixpkgs
   SHA and pinned evaluator; verify identity/version and materialize sources
   before reading them. Inspect `doc/README.md`, `doc/nav.json`,
   `doc/manpage-urls.json`, generator/renderer definitions, selected chapters,
   catalogue, library comments and notices. Build `nixpkgs-manual.lib-docs` as a
   separate derivation and inspect its actual JSON schema. Record unambiguous
   anchor IDs with expected headings and exact API identities/explicit aliases.
   Missing selections require a documented decision, not guessed substitutes.

   Initial reference scope:

   - `packaging.md`: selected sections of `doc/stdenv/stdenv.chapter.md` for
     stdenv use, dependency overview, fixed-point arguments, phase control,
     check/install phases, `runHook`, substitution and setup hooks; selected
     description/license/maintainers/main-program/platform metadata from
     `doc/stdenv/meta.chapter.md`; package tests from
     `doc/stdenv/passthru.chapter.md`.
   - `customization.md`: `override`, `overrideAttrs` and `overrideDerivation`
     limitations from `doc/using/overrides.chapter.md`; defining and explicitly
     applying overlays from `doc/using/overlays.chapter.md`; generic module
     introduction and focused `lib.evalModules` arguments/results from
     `doc/module-system/module-system.chapter.md`, retaining its incompleteness
     notice.
   - `helpers.md`: `doc/build-helpers.md`; caveats/hash guidance and `fetchurl`,
     `fetchzip`, `fetchFromGitHub` from `doc/build-helpers/fetchers.chapter.md`;
     `runCommand`, `writeText`, `writeShellApplication` from
     `doc/build-helpers/trivial-build-helpers.chapter.md`; selected content from
     `doc/build-helpers/special/mkshell.section.md`; short Python
     package/application, JavaScript `buildNpmPackage`, Go `buildGoModule`, and
     Rust `buildRustPackage` entry sections from `doc/languages-frameworks/`.
   - `library.md`: generated records for `lib.attrsets.attrByPath`,
     `lib.attrsets.mapAttrs`, `lib.attrsets.mapAttrsToList`,
     `lib.attrsets.optionalAttrs`, `lib.attrsets.recursiveUpdate`,
     `lib.lists.optionals`, `lib.lists.unique`, `lib.strings.escapeShellArg`,
     `lib.strings.concatMapStringsSep`, `lib.customisation.callPackageWith`,
     `lib.fixedPoints.composeExtensions`, and `lib.fileset.toSource`.

   Verify: every selection exists at the pin and the generated records preserve
   available descriptions, arguments, types, examples and source declarations.
   Introductory selections must not implicitly include entire child chapters.
   Avoid full language/framework chapters and configuration-option catalogues.

3. **Implement focused conversion in `scripts/nixpkgs.py`.** Reuse code/fence and
   other helpers only where behavior matches. Build a source-derived anchor index
   including selected generated-library records. Preserve explicit heading and
   inline anchors with unique package targets; resolve empty link labels from
   actual titles. Prefer bundled links, otherwise verified manual targets or
   pinned source-file citations identifying the section in prose. Never invent
   GitHub fragments for custom anchors; label live unstable-manual links as
   supplementary and moving. Reject duplicate, missing or ambiguous targets.

   Preserve admonition labels/nesting, example titles, inherited warnings and
   compatibility context. Convert supported literal/manpage roles using pinned
   mappings and retain definition-list argument relationships. Preserve fenced
   executable text, interpolation and meaningful indentation. Treat documentation
   include fences separately: resolve only selected supported includes inside
   the checkout, record hashes, and reject cycles/traversal/ambiguous scope.
   Resolve only generated substitutions actually needed by selected excerpts.
   Unknown syntax, placeholders, directives, schema changes or absent API records
   fail before replacement. Never execute documentation snippets.
   Verify with focused fixtures drawn from real selected syntax, including error
   paths and byte preservation of code. No full site or custom Nix-comment parser.

4. **Implement the isolated semantic/build checks.** Add a small fixture and
   checks under `tests/nixpkgs/`, invoked by generation/`--check` and CI. Import
   the candidate source using the fixed evaluator, explicit configuration and
   platform. Assert `callPackage` argument overrides, `overrideAttrs`, overlay

   small `evalModules` composition. Evaluate relevant language-helper availability

   Build a local-source `stdenvNoCC` fixture proving pre/post hooks, checks and
   installed output, plus a small shell-application helper. Assert observable
   output. Avoid application-source fetching, service startup, user-project

   Verify with the actual pinned tools and record platform/build limitations.

5. **Create the package and integrate shared maintenance.** Write the concise
   `SKILL.md` and generated four references, manifest and `COPYING`, with contents

   hashes, notices and exact package membership; run the skill-creator validator

   After step 1's integration prerequisite is satisfied, extend `scripts/update.py`,
   `scripts/check.py` and `scripts/artifact.py` for the explicit third identity

   do not claim power-loss atomicity. Automatic writes may affect only the four

   branch policy, code, tests, workflows and sibling packages.
   Verify unchanged and changed updates, provenance-only reports, ancestry and

## Tests

```sh
python3 -m unittest discover -s tests -p 'test_*.py'
python3 scripts/check.py
python3 scripts/update.py --check
python3 scripts/check.py --skill devenv-project
python3 scripts/update.py --skill devenv-project --check
python3 scripts/check.py --skill nixpkgs-development
python3 scripts/update.py --skill nixpkgs-development --check
python3 scripts/update.py --skill nixpkgs-development --check
actionlint
git diff --check
git diff --exit-code <integration-base> -- skills/nix-language skills/devenv-project
```

Expected: checks pass, repeated regeneration changes no package bytes, controlled
evaluation/build assertions succeed, and sibling diff is empty. The Nixpkgs
validation path must invoke its semantic/build checks rather than leave them as
an optional manual step. Test explicit revision and latest modes in disposable
copies, preserving real package pins.

Focused regression cases cover custom/inline anchors, empty labels, cross-chapter
links, supported admonitions/roles/definition lists, inherited caveats, include
resolution and code preservation; absent/duplicate/malformed/unknown/cyclic/
escaping inputs; generated-API/schema changes; serialization determinism;
ancestry/rewind/divergence/unavailable-source failures; staging and partial-write
restoration; policy/toolchain mutation; sibling isolation; changed/no-op and
malicious/stale artifacts. Validate actual pinned source/declaration targets and
any supplementary public links included in the package.

## Rollback

Before merge, revert implementation commits on this task branch and rerun sibling
checks, retaining the approval history. After merge, use a reviewed revert PR for
the Nixpkgs package/tooling/workflow changes. If updates fail, keep the last
validated package and disable only the Nixpkgs update path if necessary; preserve
sibling schedules. Consumers can reinstall the entire skill from the previous
known-good repository commit. No host configuration, user trust or installed
agent files should require restoration because this work does not modify them.
