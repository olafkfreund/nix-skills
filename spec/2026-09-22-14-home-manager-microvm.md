# Spec: Home Manager and microvm.nix skills

## Design

Add two independent portable packages, registered as `home-manager` and
`microvm-nix`. Each package keeps an authored `SKILL.md` and generated,
revision-pinned references, provenance, and license files.

### Home Manager package

Source: `https://github.com/nix-community/home-manager`, default branch
`master`, with the exact commit recorded in `sources.json`.

Curate these documentation areas into separate references:

- `docs/manual/nix-flakes/nixos.md` for NixOS-module integration.
- `docs/manual/usage/configuration.md` for user configuration structure.
- `docs/manual/usage/dotfiles.md` for file management.
- `docs/manual/usage/modular-services.md` for service modules.
- `docs/manual/writing-modules.md` for extending Home Manager.

The authored instructions will emphasize the NixOS-module workflow used by
this collection, stable `home.stateVersion`, module reuse, and validation.
They will not copy the complete generated option catalogue; option lookups will
link to the pinned upstream manual or the user's actual Home Manager revision.

### microvm.nix package

Source: `https://github.com/microvm-nix/microvm.nix`, default branch `main`,
with the exact commit recorded in `sources.json`.

Curate these documentation areas into separate references:

- `doc/src/intro.md` and `doc/src/declaring.md` for the module and VM shape.
- `doc/src/declarative.md` for embedded versus flake-based deployment.
- `doc/src/host.md` and `doc/src/host-systemd.md` for host integration.
- `doc/src/options.md` for the option surface and defaults.
- `doc/src/simple-network.md`, `doc/src/routed-network.md`, and
  `doc/src/interfaces.md` for network choices.
- `doc/src/shares.md` for host-to-guest filesystem sharing.

The authored instructions will distinguish VM configuration from host
management, document the update behavior of existing deployments, and call out
host-path and network trust boundaries.

### Provider and update behavior

Add explicit maintained-source provider modules for the two upstreams, reusing
the existing updater primitives and artifact publication boundary. The
providers will:

1. Resolve and validate the configured default-branch commit with
   `git ls-remote`.
2. Fetch that exact revision through the existing Nix source-fetching path.
3. Read only the approved paths, rejecting missing paths, traversal, unexpected
   document structure, unsupported directives, and unclosed code fences.
4. Preserve fenced examples while adapting relative links to pinned upstream
   source URLs and checking external documentation links.
5. Generate only approved reference files, the upstream `LICENSE`, and
   `sources.json`; authored `SKILL.md` remains untouched.
6. Record source path hashes, selected revision, license hash, and output hashes.
7. Compare regenerated bytes during `--check`, publish atomically through the
   existing staging/artifact boundary, and produce a changed-input report.

The existing CLI dispatch, provider checks, artifact allowlists, unit-test
matrix, scheduled update matrix, and per-skill automation branches will be
extended for both names. Registering a skill in `skills.json` will remain
separate from enrolling it in scheduled updates; the provider matrix is the
explicit maintenance enrollment.

Use the smallest shared helper only where the two providers have identical
Markdown/link behavior. Keep source-specific parsing and policy in separate
provider modules so a Home Manager documentation change cannot silently weaken
microvm.nix validation.

### Provenance and licensing

Copy each upstream repository's root `LICENSE` unchanged into its package and
link it from generated references. Record the source URL, branch, revision,
selected paths, input hashes, transformations, and output hashes in
`sources.json`. Generated headers will identify the upstream revision and state
that the references are modified excerpts. No upstream file is copied beyond
the selected references and required license.

## Alternatives rejected

- **Install the upstream documentation trees as skills:** rejected because they
  are not portable `SKILL.md` packages and would not provide stable trigger
  instructions or collection provenance.
- **Copy the complete manuals:** rejected because it creates large, stale
  packages and makes review of upstream changes impractical.
- **One combined Home Manager/microvm skill:** rejected because the domains have
  different triggers, source trees, and update policies.
- **A generic updater that treats every Markdown file identically:** rejected
  unless implementation proves the shared behavior safe; source-specific
  validation is more important than reducing a small amount of code.
- **Add a new privileged updater service:** rejected because the current
  scheduled artifact workflow already provides scoped generation and PRs.

## Risks

- Both upstream default branches are moving targets; branch resolution must
  reject malformed or ambiguous refs and preserve the previous pin when a
  revision disappears.
- Documentation formats or link conventions may change. Providers must fail
  closed rather than silently publish truncated or mislinked references.
- Home Manager's generated manuals and option pages may expand substantially;
  the initial selection deliberately avoids bundling the full option catalogue.
- microvm.nix documentation includes host paths, networking, and device
  passthrough. The skill must explain boundaries without turning documentation
  into executable host changes.
- License or notice changes require a reviewed provider/package update and must
  not be hidden by an automated regeneration.
- Extending the update matrices and artifact allowlists can accidentally permit
  cross-skill writes; tests must verify each provider can modify only its own
  generated files.

## Verification

- Offline collection validation accepts exactly the two new package directories
  and sorted registry entries, with exactly the required frontmatter fields.
- Provider unit tests cover branch/revision validation, selected-path
  confinement, Markdown conversion, fenced-code preservation, link failures,
  license handling, deterministic manifests, no-op updates, and atomic publish
  rollback.
- `python3 scripts/check.py --skill home-manager` and
  `python3 scripts/check.py --skill microvm-nix` validate provenance and package
  boundaries.
- `python3 scripts/update.py --skill <name> --check` proves regeneration is
  reproducible against each pinned upstream revision without modifying files.
- `python3 -m unittest discover -s tests -p 'test_*.py'`,
  `devenv shell check-fast`, `nix flake check`, the package build, and the
  aarch64 evaluation pass.
- `actionlint` validates the expanded scheduled update and PR-check matrices.
- A manual review confirms the generated reports, source citations, license
  files, and that authored `SKILL.md` files are never replaced by updates.
